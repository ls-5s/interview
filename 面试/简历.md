# 面试官问「WebSocket 消息防抖与批量更新」怎么回答？

在我们的实时协作场景（比如多人任务状态同步、实时编辑、评论推送）中，WebSocket 会高频推送消息。比如用户频繁修改任务状态、多人同时操作时，短时间内会产生大量重复 / 连续的消息，导致三个问题：
前端性能问题：每条消息都触发状态更新 + 视图渲染，造成页面卡顿、渲染阻塞；
网络压力问题：大量消息频繁传输，增加带宽占用，甚至导致消息阻塞、丢包；
无效更新问题：短时间内同一资源的多次状态变更，中间状态是无意义的，只需要最终状态。
为了解决这些问题，我们对 WebSocket 消息做了防抖消抖 + 批量更新两层优化，同时配套了稳定性保障机制。

二、核心优化实现（分两部分讲）

1. WebSocket 消息防抖实现
定义防抖缓存 Map，key 为消息类型 + 资源 ID，value 存储定时器和最新消息；设置固定防抖时间窗口，收到消息时，清除对应 key 的旧定时器，创建新定时器并保存最新消息；定时器触发后，仅处理最后一条消息，完成后清除缓存。
防抖实现（极简背诵版）
用 Map 按消息类型 + 资源 ID 存储定时器；收到新消息就清除旧定时器、重新计时；时间到后，只处理最后一条消息，处理完清空缓存。
2. 批量更新实现
维护消息队列、批量时间窗口和最大处理条数；收到消息先推入队列，未启动定时器则创建批量定时器；队列达到最大条数或定时器触发时，清空定时器和队列，批量处理所有消息，统一更新状态并渲染视图。

# 数据与权限优化：将频繁遍历的数组查找改为 Map 预计算缓存，时间复杂度从 O (n) 降为 O (1)，渲染计算减少 80% 数据权限校验（制片人 / 导演 / 美术）

优化前问题项目中需要频繁根据 ID 查找对应数据，比如任务状态同步、用户角色权限校验，之前每次查找都要遍历整个数组，时间复杂度是 O (n)。当数据量变大（比如任务列表超过 100 条）时，每次渲染都要多次遍历，导致页面卡顿、渲染延迟。
优化方案我在数据初始化的时候，先把数组转换成一个 Map，以「ID 为 key、数据为 value」的形式做预计算缓存。后续所有需要根据 ID 查找数据的操作，都直接从 Map 中读取，时间复杂度直接降到 O (1)。
优化效果改造后，单次查找的耗时从和数据量成正比，变成了固定时间，整体渲染效率提升了 80% 以上，页面卡顿问题完全解决，在大数据量场景下也能保持流畅。
三、带伪代码的技术细节版（如果面试官追问实现）

```js
// 优化前：每次都遍历数组，时间复杂度 O(n)
function findDataById(id, list) {
  return list.find(item => item.id === id)
}

// 优化后：预计算 Map 缓存，时间复杂度 O(1)
function initDataMap(list) {
  const map = new Map()
  list.forEach(item => {
    map.set(item.id, item)
  })
  return map
}

// 初始化时一次性生成缓存
const dataMap = initDataMap(originalList)

// 使用时直接读取
function findDataById(id) {
  return dataMap.get(id)
}
```

我会在数据加载完成时，一次性把数组转成 Map 缓存，只做一次 O (n) 的遍历；
后续所有查找操作，都直接用 map.get(id) 读取，变成 O (1)；
同时我也加了缓存更新逻辑，当数据增删改时，同步更新 Map，保证数据一致性。

# 基于 RBAC 实现前端权限控制

RBAC 即基于角色的权限控制，核心逻辑：用户 → 绑定角色 → 角色关联权限，前端通过接口获取用户的角色和权限列表，做路由、菜单、按钮三层权限管控。
具体实现（背这 5 步，面试直接说）
登录获取权限用户登录后，后端返回当前用户的角色和权限标识集合（如路由路径、按钮 code），我存在 Pinia 全局状态中持久化。
动态路由权限前端定义所有路由，标记权限字段；通过路由守卫，用用户权限过滤出可访问路由，再用 addRoute 动态注册，无权限路由直接拦截跳转 403。
侧边菜单权限根据过滤后的动态路由，动态渲染侧边栏菜单，无权限菜单直接隐藏。
按钮 / 元素权限封装自定义指令 v-permission，传入按钮权限码，和全局权限列表比对，无权限直接隐藏 / 禁用按钮。
全局守卫兜底路由全局守卫校验权限，防止用户手动输入路径非法访问，实现全链路权限控制。

# 前端 RBAC 权限控制 完整核心代码

 1. Pinia 全局状态（存储用户、角色、权限）

```typescript
// stores/permission.js
import { defineStore } from 'pinia'

export const usePermissionStore = defineStore('permission', {
  state: () => ({
    // 用户角色
    role: '',
    // 权限标识集合（按钮/接口）
    permissions: [],
    // 最终可访问的路由
    routes: []
  }),
  actions: {
    // 登录后设置用户权限
    setUserInfo({ role, permissions }) {
      this.role = role
      this.permissions = permissions
    },
    // 设置可访问路由
    setRoutes(routes) {
      this.routes = routes
    }
  },
  persist: true // 持久化（刷新不丢失）
})
```

1. 路由配置（静态路由 + 动态路由）

```javascript
// router/index.js
import { createRouter, createWebHistory } from 'vue-router'

// 静态路由（所有人都能访问：登录、404）
export const constantRoutes = [
  { path: '/login', component: () => import('@/views/Login.vue') },
  { path: '/403', component: () => import('@/views/403.vue') }
]

// 动态路由（需要权限控制）
export const asyncRoutes = [
  {
    path: '/task',
    component: () => import('@/views/Task.vue'),
    meta: { role: ['制片', '导演', '美术'] } // 可访问角色
  },
  {
    path: '/workbench',
    component: () => import('@/views/Workbench.vue'),
    meta: { role: ['制片', '导演'] }
  }
]

const router = createRouter({
  history: createWebHistory(),
  routes: constantRoutes
})

export default router
```

 1. 动态路由 + 路由守卫（核心）

```javascript
// 路由守卫
import { usePermissionStore } from '@/stores/permission'
import router from './index'
import { asyncRoutes, constantRoutes } from './index'

// 过滤有权限的路由
function filterAsyncRoutes(routes, role) {
  return routes.filter(route => {
    if (route.meta?.role) {
      return route.meta.role.includes(role)
    }
    return true
  })
}

// 全局守卫
router.beforeEach((to, from, next) => {
  const store = usePermissionStore()
  
  // 已登录
  if (store.role) {
    if (to.path === '/login') return next('/')

    // 没有生成过动态路由
    if (store.routes.length === 0) {
      // 1. 过滤有权限的路由
      const accessRoutes = filterAsyncRoutes(asyncRoutes, store.role)
      // 2. 动态添加路由
      accessRoutes.forEach(route => router.addRoute(route))
      // 3. 保存到pinia
      store.setRoutes([...constantRoutes, ...accessRoutes])
      
      return next({ ...to, replace: true })
    }

    next()
  } else {
    // 未登录
    next('/login')
  }
})
```

1. 自定义指令 v-permission（按钮权限）

```javascript
// directive/permission.js
import { usePermissionStore } from '@/stores/permission'

// 注册全局指令
export default (app) => {
  app.directive('permission', {
    mounted(el, binding) {
      const { permissions } = usePermissionStore()
      const value = binding.value // 传入的权限码 如 delete:asset
      
      // 没有权限 → 移除/禁用按钮
      if (!permissions.includes(value)) {
        el.style.display = 'none'
        // 或者禁用 el.disabled = true
      }
    }
  })
}

// main.js 引入
import directive from '@/directive/permission'
const app = createApp(App)
app.use(directive)
```

# 渲染性能优化：针对长列表（300+条目）卡顿问题，引入虚拟滚动与图片懒加载，减少 DOM 数量 70%，滚动帧率从 20fps 提升至 50fps 以上

针对这个问题，我做了两项针对性渲染优化：
优化前，前端直接全量渲染所有列表项，导致页面生成大量冗余 DOM，浏览器频繁重排重绘，滚动时严重卡顿，帧率仅20fps 左右，用户体验很差。

1. 虚拟滚动优化我基于 Vue3 集成了虚拟滚动方案，核心是给列表容器设置固定高度与滚动区域，通过监听滚动位置，只计算并渲染可视区域内的列表项，视口外的条目不生成 DOM；同时用一个占位 div 撑起列表总高度，保证滚动条正常。这样从根源上减少 DOM 渲染数量，避免大量 DOM 导致的渲染阻塞。

=======================

虚拟滚动 实现原理（腾讯面试标准答案，清晰不绕弯，逐字背）
核心一句话
虚拟滚动的原理是：只渲染可视区域内的列表项，视口外的内容不生成 DOM，通过滚动计算动态切换渲染内容，并用占位元素撑起总高度，实现长列表流畅滚动。
详细原理（分 5 步，面试逻辑满分）
设置固定可视容器
给列表外层包裹一个固定高度的容器，并开启纵向滚动，明确可视区域范围。
计算基础参数
提前确定每一行的固定高度，根据容器高度 ÷ 行高，算出可视区域能容纳的条目数量。
监听滚动位置
监听容器的滚动事件，通过滚动偏移量，计算出当前需要渲染的起始索引、结束索引。
动态渲染可视区域数据
只根据起止索引，渲染对应区间的列表数据，视口外的数据不创建 DOM 节点，从根源减少 DOM 数量。
占位撑高保证滚动条正常
用一个空白占位 div，设置高度 = 单条高度 × 总数据量，撑起完整的滚动条高度，让滚动效果和真实列表完全一致

1. 图片懒加载优化列表内包含素材图片、用户头像等资源，我使用IntersectionObserver API封装了图片懒加载指令，图片默认不加载真实资源，只有进入可视区域后才替换 src 发起请求，减少首屏网络请求与渲染压力。
最终优化效果非常明显：DOM 节点数量减少 70%，浏览器重排重绘频率大幅降低，滚动帧率稳定在50fps 以上，长列表滚动完全流畅，彻底解决卡顿问题。

我在项目里针对列表的用户头像、素材图片，用 IntersectionObserver 浏览器原生 API 封装了 Vue 自定义指令实现图片懒加载：

1. 图片默认不填真实 src，用 data-src 存真实图片地址，避免首屏批量请求；
2. 通过 API 监听图片是否进入浏览器可视区域；
3. 图片进入可视区后，自动把 data-src 赋值给 src，浏览器才真正加载图片；
4. 加载完成后关闭监听，节省性能。最终大幅减少首屏网络请求，降低页面渲染压力。

# 针对 LLM 输出不稳定问题，设计三级解析机制（正则 + JSON + 兜底），显著提升结果稳定性，降低人工复核成本

一级解析：正则前置清洗
先用正则表达式过滤掉 LLM 输出里的无关内容，比如多余的文字说明、```json 标记、注释、空格换行等干扰字符，只提取出纯 JSON 格式的核心内容，为后续解析扫清障碍。
二级解析：JSON 严格校验解析
对清洗后的内容执行 JSON.parse 解析，并校验业务必填字段是否完整、字段类型是否符合要求；解析成功且字段合规，则直接进入业务流程，作为核心解析链路。
三级解析：兜底容错处理
如果前两步解析失败（比如 JSON 格式仍损坏、字段缺失），启动兜底策略：通过关键词匹配、字段模糊提取的方式，抓取关键业务数据，组装成默认合规的 JSON 结构返回，保证业务流程不中断、不报错。
最终效果：LLM 输出解析成功率显著提升，几乎不再出现解析崩溃的情况，大幅降低了人工复核的成本，系统稳定性明显增强。

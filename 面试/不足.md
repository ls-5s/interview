# script标签async/defer的区别与作用 ?

两者都是解决同步 JS 阻塞 HTML 解析的方案，让外部 JS 脚本异步并行下载，不阻塞页面 DOM 构建，避免单线程 JS 导致页面白屏。

<!-- 注意：仅对外部脚本生效，内联 <script> 加这两个属性无效。 -->

二、核心区别（面试必背 4 点）

1. 执行时机
defer：等待整个 HTML 解析完成后，再执行 JS
async：JS 下载完成后立即执行，此时 HTML 可能还在解析
2. 执行顺序
defer：严格按照脚本在 HTML 中出现的顺序执行（保证依赖顺序）
async：谁先下载完谁先执行（乱序，无依赖关系）
3. 与 DOMContentLoaded 关系
defer：在 DOMContentLoaded 事件之前执行，会等所有 defer 脚本执行完再触发该事件
async：与 DOMContentLoaded 无关，执行时机完全看下载速度（可能早于 / 晚于该事件）
4. 适用场景
defer：需要操作 DOM、依赖其他脚本（如先加载 jQuery 再加载业务代码）、必须保证执行顺序的脚本
async：独立无依赖的脚本（如埋点、广告 SDK、统计脚本），不需要操作 DOM、不依赖其他文件
三、一句话对比记忆
defer：异步下载，HTML 解析完再按顺序执行 → 有序、晚执行
async：异步下载，下载完立即执行 → 无序、早执行
四、图示化总结（面试口述版）
同步 script：下载 + 执行 → 阻塞 HTML 解析
defer script：并行下载 → HTML 解析完毕 → 按序执行
async script：并行下载 → 下载完成 → 立即执行（可能中断 HTML 解析）

# 不知道 JS 在页面渲染中阻塞 HTML/CSS 解析的具体时机

1. 同步 <script> 阻塞 HTML 解析的精确时机
浏览器从上往下解析 HTML：
一旦遇到普通同步 script 标签（无 async/defer）
立刻暂停 HTML 解析（DOM 构建停止）
下载（外部 JS）并立即执行 JS
执行完毕后，才恢复 HTML 解析
原因：浏览器怕 JS 用 document.write 或修改 DOM，必须等执行完再继续解析。
2. JS 间接阻塞 CSS 解析 / 渲染的时机
CSS 解析不会直接阻塞 HTML 解析
但 CSSOM 没构建完，会阻塞后面 JS 的执行
流程：
遇到 CSS → 加载解析 CSS → 再执行 JS → JS 阻塞 HTML
最终表现：CSS 间接阻塞了 HTML 解析
3. JS 阻塞页面渲染的时机
页面渲染（显示内容）必须等 DOM + CSSOM 都完成
JS 阻塞 HTML → DOM 构建暂停
CSS 阻塞 JS → CSSOM 构建暂停
两者都不全 → 渲染树无法生成 → 页面白屏、不渲染
4. 不阻塞的情况
带 async / defer 的外部脚本
下载 JS 时不阻塞 HTML 解析
只有执行时可能短暂阻塞（async），或完全不阻塞（defer）

同步 JS 碰到就堵 HTML；CSS 不堵 HTML 但堵 JS；JS 一执行，DOM 构建和页面渲染全停。

# Promise 静态方法：不了解Promise.all/race/any/allSettled的用法与使用场景

一、先记住：哪些是静态方法
Promise.resolve()
Promise.reject()
Promise.all()
Promise.race()
Promise.allSettled()
Promise.any()

1. Promise.resolve(value)
作用：快速创建一个已成功的 Promise。
语法
js
Promise.resolve(值)
场景
把普通值包装成 Promise，统一异步接口
函数需要返回 Promise，但逻辑是同步成功
示例

```js
function getUser() {
  // 直接返回成功态 Promise
  return Promise.resolve({ name: 'jack' })
}
```

1. Promise.reject(reason)
作用：快速创建一个已失败的 Promise。
场景
快速抛出异步错误
统一接口返回失败
示例

```js
function login() {
  return Promise.reject(new Error('未登录'))
}
```

1. Promise.all([p1, p2, p3])
核心：全部成功才成功，一个失败就整体失败。
特点
等待所有 Promise 完成
结果数组顺序和传入顺序一致
任何一个 reject，立刻整体 reject
场景
并发请求，缺一不可
多接口数据必须全部拿到再渲染
示例

```js
Promise.all([p1, p2, p3])
  .then(values => {
    // [p1结果, p2结果, p3结果]
  })
  .catch(err => {
    // 任意一个失败都会进这里
  })
```

1. Promise.race([p1, p2, p3])
核心：谁先完成（不管成功失败），谁就是结果。
场景
请求超时控制
多服务器选最快响应
示例（超时控制）

```js
const timeout = new Promise((_, reject) =>
  setTimeout(() => reject('超时'), 3000)
)

Promise.race([fetch('/api'), timeout])
```

1. Promise.any([p1, p2, p3])
核心：只要有一个成功就成功，全部失败才失败。
和 race 区别：
race：谁先完成算谁（失败也算）
any：只看第一个成功，失败会被忽略
场景
多接口重试 / 备用接口，只要一个通就行
示例

```js
Promise.any([api1, api2, api3])
  .then(res => {})
  .catch(err => {
    // 全部失败才进这里
  })
```

# 掌握 i18n 国际化原理

一、i18n 国际化到底是什么原理？
一句话原理：前端提前存好多语言包 → 根据当前语言类型 → 自动匹配对应文字 → 渲染到页面。
二、核心流程（4 步，背这个）
定义语言包
zh.js 放中文
en.js 放英文
键名完全一样，值不同
创建 i18n 实例
注册所有语言
设置默认语言
全局注入
让所有组件能使用 $t('key') 或 t('key')
切换语言
修改当前语言类型
页面自动刷新显示对应文字

具体切换过程（3 步）
你有多个语言包

```js
const messages = {
  zh: { hello: '你好' },
  en: { hello: 'Hello' }
}
```

i18n 内部维护一个当前语言变量

```js
const currentLocale = ref('zh')
```

切换时，只需要改这个变量

```js
const changeLang = () => {
  currentLocale.value = 'en'
}
```

页面里的 t('hello') 会自动响应式更新因为 currentLocale 变了 → 重新从语言包取值。

# 固定容量缓存类实现：未按要求用Class实现，逻辑混乱，不理解简易 LRU 缓存思路

```js
class LRUCache {
  constructor(capacity) {
    // 最大容量
    this.capacity = capacity
    // 用 Map 存数据，同时保留访问顺序
    this.cache = new Map()
  }

  // 获取数据
  get(key) {
    if (!this.cache.has(key)) return -1

    // 先删除再重新 set → 变成“最近使用”，放到最后
    const val = this.cache.get(key)
    this.cache.delete(key)
    this.cache.set(key, val)

    return val
  }

  // 存入数据
  put(key, value) {
    // 如果已存在，先删掉，保证更新顺序
    if (this.cache.has(key)) {
      this.cache.delete(key)
    }

    // 满了 → 删除最久未使用（Map 最前面那个）
    if (this.cache.size >= this.capacity) {
      const oldestKey = this.cache.keys().next().value
      this.cache.delete(oldestKey)
    }

    // 新数据放到最后
    this.cache.set(key, value)
  }
}
```
